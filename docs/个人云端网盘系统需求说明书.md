# 个人云端网盘系统技术架构设计说明书

**版本：V1.0**  
**对应需求：PRD V2.0**  
**设计范围：Web PC、管理后台、核心 API、文件处理、存储与检索**  
**架构形式：模块化单体 + 异步任务 Worker + 独立基础服务**  
**技术选型基准：2026 年 11 月**  
**状态：初版技术方案**

# 一、架构设计目标

## 1.1 总体目标

系统需要具备完整的个人文件管理、多用户共享、文件预览、文件检索、版本管理、私密空间与多存储适配能力。

整体技术架构遵循以下原则：

1. **业务逻辑与物理存储分离**：文件管理模块不直接依赖本地磁盘或某一家云存储 SDK。
2. **目录层级与搜索分离**：目录树使用结构化数据库，全文检索使用独立倒排索引。
3. **文件原件与派生资源分离**：缩略图、转码视频、Office 预览文件均作为可重新生成的派生对象。
4. **核心服务与重任务分离**：普通 API 不同步执行大型转码、全文解析或 Office 转换。
5. **用户界面与第三方组件分离**：预览组件保留自身处理能力，但外层窗口、工具栏和主题由系统统一控制。
6. **共享授权与文件归属分离**：共享只建立访问关系，不复制或转移实际文件。
7. **优先选择成熟技术**：对复杂编解码、Office 渲染、文件解析等不重复造轮子。
8. **避免过早微服务化**：先完成模块边界，随后根据资源消耗与业务规模拆分部署。

## 1.2 非目标

首期不包括：

- 完整的 Office 在线协同编辑。
- 微服务治理平台。
- Kubernetes 集群部署。
- AI 自动文件分类。
- 全类型文件内容语义理解。
- 视频实时编辑或多轨剪辑。
- 端到端零知识加密。
- 实时跨设备文件同步引擎。

以上能力应预留必要接口，但不提前引入高复杂度基础设施。

### UI 选型理由

不建议直接使用大型后台 UI 组件库承担全部文件工作台界面。

网盘的核心交互涉及文件树、右键菜单、上传面板、多选、拖拽、预览弹层和大量浮动工具栏，使用高层封装过重的组件库容易导致交互与主题受限。

推荐：

**shadcn-vue + Reka UI + Tailwind CSS + 业务自研组件。**

其中：

- 对话框、菜单、下拉、弹出层优先使用成熟组件。
- 文件树、文件网格、上传任务面板采用业务组件。
- 所有颜色、圆角、阴影、字号通过统一 Design Tokens 管理。
- 用户端和管理后台可以使用同一套基础设计系统，但各自拥有独立布局。

不建议同时混用多套完整 UI 组件库。

## 3.2 模块化单体设计

推荐把文件相关业务拆成内部模块，而不是立即拆成独立微服务。

模块包括：

- `auth`：认证与会话。
- `user`：用户及用户配置。
- `space`：空间与成员。
- `file`：文件节点与目录操作。
- `upload`：上传会话与传输。
- `storage`：物理存储。
- `version`：文件版本。
- `share`：分享及共享权限。
- `search`：元数据与全文检索。
- `preview`：预览任务及资源。
- `message`：消息中心。
- `system`：系统设置。
- `task`：后台任务。
- `audit`：操作审计。

### 模块依赖原则

文件模块可以使用存储模块提供的接口，但不能调用某种存储的具体实现。

共享模块负责授权关系，文件模块只向其提供资源信息和所需的权限上下文。

搜索模块不得直接成为文件数据的权威来源。

预览模块只产生派生资源，不能修改原件。

# 四、文件树与数据库结构设计

## 4.1 核心问题

文件夹可能存在大量嵌套，例如：

```text
工作空间
 └─ 项目
    └─ 2026
       └─ 后端
          └─ Java
             └─ Spring
                └─ Security
                   └─ 认证
                      └─ 登录实现.java
```

需要支持：

- 任意层级展开。
- 当前目录文件查询。
- 查询所有后代文件。
- 搜索某个文件。
- 文件夹移动。
- 跨空间移动。
- 子树统计。
- 文件夹权限继承。

不能简单地每次请求都从根目录递归读取整个文件树。

## 4.2 目录结构方案对比

| 模型 | 查询直属子级 | 查询整棵子树 | 移动目录 | 复杂度 |
|---|---|---|---|---|
| 邻接表 | 很好 | 需要递归 | 简单 | 低 |
| 物化路径 | 很好 | 路径前缀查询 | 需更新后代路径 | 中 |
| 闭包表 | 很好 | 很好 | 需维护祖先关系 | 中高 |
| Nested Set | 一般 | 很好 | 更新复杂 | 高 |

### 最终建议

采用：

**邻接表作为权威目录结构 + 按需维护闭包表作为层级查询加速结构。**

V1 即保留层级关系模型，但闭包表可以在需要递归搜索、权限继承和子树统计时正式启用。

不推荐使用 Nested Set 作为主模型，因为网盘存在频繁的目录移动、重命名和新增操作。

## 4.3 文件节点表

建议统一使用 `file_node` 表管理逻辑文件与文件夹。

核心字段：

```sql
CREATE TABLE file_node (
    id BIGINT PRIMARY KEY,
    space_id BIGINT NOT NULL,
    parent_id BIGINT NOT NULL DEFAULT 0,

    node_type VARCHAR(16) NOT NULL,
    name VARCHAR(255) NOT NULL,

    current_version_id BIGINT NULL,

    hidden BOOLEAN NOT NULL DEFAULT FALSE,
    sort_order BIGINT NOT NULL DEFAULT 0,

    revision BIGINT NOT NULL DEFAULT 0,

    created_by BIGINT NOT NULL,
    created_at DATETIME(3) NOT NULL,
    updated_at DATETIME(3) NOT NULL,
    deleted_at DATETIME(3) NULL,

    INDEX idx_parent (
        space_id, parent_id, deleted_at, sort_order, id
    ),

    INDEX idx_space_name (
        space_id, name
    ),

    INDEX idx_space_type (
        space_id, node_type, deleted_at
    )
);
```

这是核心字段示意，不是最终生产 DDL；同名冲突、软删除唯一性及外键策略需另行补齐。

业务标识使用 `BIGINT` 时，API JSON 必须以字符串传输，避免 JavaScript 超过安全整数范围。

## 4.4 当前目录查询

例如：

```sql
SELECT *
FROM file_node
WHERE space_id = ?
  AND parent_id = ?
  AND deleted_at IS NULL
ORDER BY sort_order, id
LIMIT 100;
```

通过 `space_id + parent_id` 复合索引定位。

**当前目录查询的成本主要取决于该目录的直属节点数量，而不是这个目录距离根节点有多少级。**

因此，文件夹嵌套 20 层并不会天然比嵌套 3 层慢很多。

## 4.5 文件树懒加载

前端初始化时只查询：

- 当前空间根节点。
- 当前展开节点的直属子节点。

每次展开文件夹时：

```text
点击展开
    ↓
检查本地缓存
    ↓
没有缓存则调用 children API
    ↓
加载当前节点的直属子目录
    ↓
更新树节点
```

不一次性查询整个空间的全部文件夹。

### 推荐接口

```http
GET /api/spaces/{spaceId}/nodes
    ?parentId={parentId}
    &nodeType=FOLDER
```

返回：

- `id`
- `parentId`
- `name`
- `nodeType`
- `hasChildren`
- `hidden`
- `permission`

`hasChildren` 可以通过维护子节点计数或受控查询得出，避免额外加载全部子级。

## 4.6 前端虚拟化

树组件应当采用：

**树结构状态 + 当前可见节点扁平化 + 虚拟列表渲染。**

示例：

```text
原始树
  A
  ├─ B
  │  ├─ C
  │  └─ D
  └─ E

展开 A、B 后

可见数组：
[A, B, C, D, E]
```

再由虚拟列表只渲染可视区域附近的节点。

采用 TanStack Virtual 负责窗口化，展开、选中、懒加载和拖拽由自定义 FileTree 组件负责。

这样能够避免因为文件树很大而生成数万个真实 DOM 节点。

## 4.7 闭包表设计

当需要查询整个文件夹的所有后代时，可以建立 `file_node_closure`。

```sql
CREATE TABLE file_node_closure (
    space_id BIGINT NOT NULL,
    ancestor_id BIGINT NOT NULL,
    descendant_id BIGINT NOT NULL,
    depth INT NOT NULL,

    PRIMARY KEY (
        space_id, ancestor_id, descendant_id
    ),

    INDEX idx_descendant (
        space_id, descendant_id, ancestor_id
    )
);
```

表中保存祖先与后代关系。

例如：

```text
A
 └─ B
    └─ C
```

记录：

```text
A → A  depth=0
A → B  depth=1
A → C  depth=2
B → B  depth=0
B → C  depth=1
C → C  depth=0
```

查询 A 的所有后代：

```sql
SELECT n.*
FROM file_node_closure c
JOIN file_node n
  ON n.id = c.descendant_id
WHERE c.space_id = ?
  AND c.ancestor_id = ?
  AND n.deleted_at IS NULL;
```

### 闭包表的取舍

优点：

- 后代查询直接。
- 祖先查询方便。
- 有利于共享文件夹权限判断。
- 有利于子树统计及筛选。

缺点：

- 增加存储空间。
- 目录移动时必须维护关系。
- 极深目录链会导致关系数量明显增长。

因此不能把闭包表理解为零成本的万能索引。

对于特别大型的目录子树移动，可采用后台任务与操作锁处理。

### 深层目录限制

产品层面不强行限制用户只能创建固定少量层级，但后端必须设置可配置的安全深度、递归次数、节点数量及处理超时保护。

避免通过极端深度结构造成数据库或服务资源耗尽。

# 五、深层目录搜索与索引方案

## 5.1 首先区分三类查询

**第一类：当前目录文件查询**

只需要 MySQL 的父节点索引。

**第二类：文件名与元数据搜索**

可以使用 MySQL 条件索引；跨大量文件的模糊搜索建议使用搜索引擎。

**第三类：文件正文全文搜索**

必须对正文建立独立可检索的数据结构，不建议每次搜索时读取文件内容。

这三类查询不应该使用完全相同的实现方式。

## 5.2 是否直接使用 MySQL？

MySQL 可以很好地处理：

- 精确文件名。
- 文件后缀。
- 空间 ID。
- 父级目录 ID。
- 文件类型。
- 时间范围。
- 文件大小范围。

例如：

```sql
SELECT *
FROM file_node
WHERE space_id = ?
  AND name = ?;
```

适合 B-Tree 索引。

但是：

```sql
WHERE name LIKE '%需求%'
```

包含前置通配符的查询通常不能有效利用普通 B-Tree 前缀索引。

即使增加普通索引，也不能自动解决任意子串匹配的问题。

对于中文模糊搜索、正文搜索和结果高亮，建议使用倒排索引。

## 5.3 全文搜索引擎对比

| 技术 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| MySQL 普通索引 | 部署简单 | 不适合复杂全文搜索 | 结构化查询 |
| MySQL FULLTEXT | 无新增服务 | 分词、相关度与扩展受限 | 小规模备选 |
| Meilisearch | 接口简单、中文支持、结果高亮 | 需要独立同步索引 | 首选 |
| OpenSearch | 全文分析及分布式能力强 | 部署和维护成本高 | 大规模扩展 |
| Elasticsearch | 成熟检索生态 | 运维复杂，许可证需评估 | 备选 |
| PostgreSQL FTS | 数据库内完成检索 | 中文及高级分词需配置 | 替代数据库方案 |

### 最终建议

**MySQL 存储真实文件元数据，Meilisearch 存储可搜索的派生索引。**

Meilisearch 不保存文件的权威归属状态，也不直接向浏览器开放管理密钥。

## 5.4 搜索索引拆分

建议设计两个逻辑索引。

### resource_index

用于搜索：

- 文件名称。
- 文件夹名称。
- 文件后缀。
- 文件类型。
- 文件路径。
- 创建时间。
- 修改时间。
- 文件大小。

文档示例：

```json
{
  "id": "10001",
  "spaceId": "2001",
  "parentId": "3001",
  "name": "系统设计文档.pdf",
  "extension": "pdf",
  "fileType": "DOCUMENT",
  "pathText": "工作空间/项目A/文档",
  "size": 102400,
  "isFolder": false,
  "deleted": false
}
```

### content_index

用于搜索正文片段。

示例：

```json
{
  "id": "10001:5:2",
  "fileId": "10001",
  "versionId": "5",
  "chunkNo": 2,
  "spaceId": "2001",
  "content": "系统采用模块化单体架构，并使用独立的文件存储适配器..."
}
```

文件正文不建议全部存进单个超大的索引文档。

将文本拆分为适当大小的片段，例如按段落边界拆分，每段控制在约 1,000—2,000 个字符，具体由基准测试调整。

搜索多个片段命中同一个文件时，按 `fileId` 聚合显示。

## 5.5 内容提取流程

```text
文件上传成功
      ↓
写入文件元数据
      ↓
创建 CONTENT_EXTRACT 任务
      ↓
Apache Tika 解析文件
      ↓
提取纯文本
      ↓
清理文本内容
      ↓
按段落切分片段
      ↓
写入 Meilisearch
      ↓
更新索引状态
```

Apache Tika 可以用于：

- PDF 文本提取。
- Word 文本提取。
- Excel 单元格内容提取。
- PowerPoint 文本提取。
- 代码与文本文件处理。
- 文件类型检测。

不要求它负责最终页面排版和预览。

## 5.6 搜索与权限的关系

搜索引擎不能独立决定某个用户是否有权限访问文件。

推荐：

1. 用户调用后端搜索 API。
2. 后端计算可访问的空间及共享资源范围。
3. 将可安全表达的范围转换为搜索过滤条件。
4. 从 Meilisearch 读取候选结果。
5. 根据数据库当前授权状态再次校验。
6. 移除无权访问、隐藏或锁定的资源。
7. 对结果进行分页与分类。
8. 返回给前端。

需要特别注意：

- 不能只取搜索结果前 20 条，过滤无权资源后就直接返回，否则可能出现空页或错误数量。
- 可以通过多批次获取候选结果补齐分页。
- 对大型系统应优化索引权限标签，减少无效候选。
- 搜索结果总数需要区分准确总数与估算值。
- 权限变更必须立即影响结果可见性，即使异步索引还没有更新。

## 5.7 搜索结果高亮

Meilisearch 提供匹配内容格式化与裁剪能力。

搜索接口可以请求：

- 名称高亮。
- 正文匹配高亮。
- 匹配片段截取。
- 匹配字段信息。

前端应当安全渲染高亮标记，不直接信任未经净化的索引文本。

示例：

```text
系统采用模块化单体架构，
文件的[存储策略]可以根据配置动态切换。
```

搜索结果同时返回命中类型：

- NAME
- FOLDER
- EXTENSION
- CONTENT
- PATH

## 5.8 索引更新一致性

文件操作与搜索引擎写入不能依赖一个跨服务数据库事务。

采用：

**业务事务 + Outbox 事件表 + 异步索引任务。**

例如重命名：

1. MySQL 事务更新名称。
2. 同一事务写入 `FILE_RENAMED` 事件。
3. 事务提交。
4. 后台 Worker 读取事件。
5. 更新 Meilisearch。
6. 标记事件完成。

任务失败时可重试。

索引更新应携带文件的内容版本或元数据修订号，防止旧事件覆盖新数据。

允许索引短暂延迟，但不能允许越权访问。

## 5.9 索引修复

必须支持：

- 单文件重新索引。
- 单空间重建索引。
- 全量重建索引。
- 失败任务重试。
- 索引状态查询。
- 索引与数据库一致性检查。

搜索索引属于可重建派生数据，不能作为文件内容的唯一副本。

# 六、统一存储架构

## 6.1 存储层目标

需要支持：

- 本地文件系统。
- 数据库存储。
- S3 兼容存储。
- 多个存储实例同时存在。
- 默认存储切换。
- 历史文件正常读取。
- 文件迁移。
- 版本与去重扩展。

## 6.2 存储适配器接口

建议定义：

```java
public interface StorageProvider {

    String put(
        String key,
        InputStream input,
        long size
    );

    InputStream get(String key);

    InputStream getRange(
        String key,
        long start,
        long endInclusive
    );

    boolean exists(String key);

    void delete(String key);

    StorageObjectInfo stat(String key);
}
```

具体接口还应考虑分片上传、多对象复制、校验与签名 URL 等可选能力。

不建议强行把每种存储后端都定义成完全相同的高级功能集。

可以使用能力接口扩展：

- MultipartCapable。
- PresignedUploadCapable。
- ServerSideCopyCapable。

## 6.3 存储适配器实现

```text
StorageService
     │
     ├─ LocalStorageProvider
     │
     ├─ S3StorageProvider
     │
     └─ DatabaseStorageProvider
```

统一通过 `storageProfileId` 查找具体配置。

## 6.4 文件实际存储引用

文件版本引用物理内容对象。

物理内容对象记录：

- 对象 ID。
- 存储实例 ID。
- Storage Key。
- 文件大小。
- SHA-256。
- 创建时间。
- 存储状态。
- 引用关系。

存储 Key 不应直接依赖用户原始文件名。

例如：

`objects/20/26/11/01HF...`

这样用户修改文件名、修改路径和跨空间移动时，不必同步修改物理对象 Key。

## 6.5 存储切换

管理员修改默认存储配置时：

1. 校验目标实例可写。
2. 更新默认存储配置。
3. 新上传会话记录选定的存储实例。
4. 新文件写入新实例。
5. 历史文件保持不变。

特别注意：上传会话应在初始化时固定目标存储实例，防止上传中途管理员切换配置导致同一次上传的分片进入不同存储。

## 6.6 数据库存储

数据库二进制存储作为可选适配器保留。

不建议大文件默认写入 MySQL BLOB。

原因包括：

- 数据库备份体积迅速扩大。
- 高并发文件读取占用数据库连接。
- 大文件上传与读取成本高。
- 数据库故障影响文件和元数据两部分。

建议为数据库存储设置较低的单文件容量限制。

## 6.7 S3 存储

推荐 AWS SDK for Java 2.x。

配置包括：

- Endpoint。
- Region。
- Bucket。
- Access Key。
- Secret Key。
- Path-style 选项。
- HTTPS。
- 自定义域名。

兼容目标包括常规 AWS S3 和符合所需 S3 API 的第三方对象存储。

不同厂商对 Multipart、Checksum、CopyObject 和签名行为可能存在差异，必须通过兼容性测试验证。

## 6.8 物理对象状态

建议：

```text
STAGING
   ↓
ACTIVE
   ↓
PENDING_DELETE
   ↓
DELETED
```

上传失败的临时对象由清理任务回收。

文件逻辑删除后，不立即销毁可能仍被历史版本、共享引用或其他逻辑文件使用的对象。

# 七、文件分片上传架构

## 7.1 上传方案选择

推荐：

**Uppy Core 管理前端上传任务，自研界面与后端上传协议。**

不强制使用 Uppy Dashboard 的预设 UI。

如果未来需要完整标准化断点续传协议，可以接入 tus / tusd。

对当前系统而言，自定义上传会话接口能更直接地适配本地、数据库、S3 和文件版本管理。

## 7.2 上传流程

```text
选择文件
   ↓
创建上传会话
   ↓
服务端验证容量与权限
   ↓
确定存储实例
   ↓
返回分片信息
   ↓
并行上传分片
   ↓
记录分片状态
   ↓
请求合并/完成
   ↓
服务端校验内容
   ↓
提交文件逻辑元数据
   ↓
触发预览与索引任务
```

## 7.3 分片策略

建议初始参数：

| 参数 | 建议值 |
|---|---|
| 默认分片大小 | 8 MiB |
| 单文件并发 | 3—4 |
| 单客户端总并发 | 4—6 |
| 分片失败重试 | 3 次 |
| 重试方式 | 指数退避 |
| 小文件 | 可直接上传 |
| 上传会话有效期 | 24 小时，可续期 |

这些是初始配置，不是固定限制。

使用 S3 Multipart 时，必须遵循其分片数量和最小分片要求；对于超大文件，需要动态提高分片大小。

## 7.4 上传接口

建议：

```http
POST /api/uploads/init

GET /api/uploads/{uploadId}

PUT /api/uploads/{uploadId}/parts/{partNo}

POST /api/uploads/{uploadId}/complete

DELETE /api/uploads/{uploadId}
```

初始化请求包含：

- 文件名称。
- 文件大小。
- 文件类型。
- 目标空间。
- 目标文件夹。
- 文件摘要（可选）。
- 同名冲突策略。

后端返回：

- uploadId。
- chunkSize。
- totalParts。
- uploadMode。
- expiresAt。
- 已完成分片。
- 临时上传授权（适用时）。

## 7.5 本地上传

本地存储可先将分片写入临时区域。

例如：

```text
tmp/uploads/{uploadId}/
   00001.part
   00002.part
   00003.part
```

全部分片完成后合并或流式写入最终对象。

需要校验：

- 分片编号。
- 单片大小。
- 整体大小。
- 文件摘要。
- 上传会话状态。
- 用户权限。

不能简单信任客户端传递的「已上传完成」。

## 7.6 S3 直传

对于 S3，可以采用预签名 Multipart Upload。

后端：

1. 创建上传会话。
2. 发起 S3 Multipart Upload。
3. 为客户端签发受限的分片上传 URL。
4. 客户端直接向 S3 上传。
5. 客户端提交分片结果。
6. 后端确认 Multipart Upload。
7. 后端校验最终对象并提交业务元数据。

优点是文件数据不必全部经过 Spring Boot API 服务。

应正确处理 URL 过期、分片校验、ETag 及未完成 Multipart 清理。

## 7.7 断点续传

浏览器重新打开上传面板时：

1. 读取本地可恢复的任务元数据。
2. 查询服务端 uploadId 状态。
3. 找出尚未上传的分片。
4. 确认用户仍授予本地文件访问权限。
5. 恢复剩余分片上传。

在普通浏览器 File API 下，页面关闭后不保证可以自动重新读取所有本地文件。

可以引导用户重新选择同一个文件并通过摘要与文件信息校验后恢复。

## 7.8 上传事务一致性

对象上传与数据库提交属于两个独立系统。

不能期望单个 MySQL 事务同时回滚已写入 S3 的数据。

采用上传状态机：

```text
INIT
  ↓
UPLOADING
  ↓
ASSEMBLING
  ↓
VERIFYING
  ↓
COMMITTING
  ↓
COMPLETED
```

失败进入：

- FAILED。
- CANCELED。
- EXPIRED。

完成接口必须幂等，防止用户重复点击完成操作而创建多个逻辑文件。

上传事务失败留下的临时对象由清理任务处理。

# 八、文件版本与去重架构

## 8.1 数据关系

```text
FileNode
   │
   └─ CurrentVersionId
             │
             ▼
         FileVersion
             │
             ▼
          BlobObject
             │
             ▼
        StorageProfile
```

其中：

- FileNode 表示逻辑文件。
- FileVersion 表示一个版本的内容。
- BlobObject 表示可复用的物理二进制对象。
- StorageProfile 表示存储实例。

## 8.2 文件版本

建议使用独立 `file_version` 表。

核心字段：

- id。
- file_id。
- version_no。
- blob_object_id。
- created_by。
- created_at。
- checksum。
- size。

一个逻辑文件可以关联多个版本。

重命名、移动不产生新版本；替换文件内容产生新版本。

## 8.3 版本上限

配置层级：

```text
系统最大上限
      ↓
用户自定义上限
      ↓
文件实际版本保留策略
```

最终有效版本数：

`effectiveLimit = min(systemLimit, userLimit)`

共享空间和共享文件夹的资源采用所属空间所有者的策略。

管理员可以统一设置最大版本数量。

## 8.4 版本清理

版本超出限制时：

1. 标记待清理版本。
2. 检查当前版本引用。
3. 删除允许清理的版本元数据。
4. 更新 BlobObject 引用关系。
5. 对无引用对象发起延迟物理删除。
6. 清理预览缓存和全文索引派生资源。

清理过程必须幂等。

## 8.5 去重架构

通过 SHA-256 建立内容标识。

但不能只依赖客户端 Hash 断言两个文件完全一致。

正确流程：

- 客户端可提前提供摘要作为候选。
- 服务端验证用户是否有权复用目标内容。
- 对新传输内容进行服务端完整性校验。
- 符合策略时复用已有物理对象。
- 新建逻辑文件或版本引用。

## 8.6 去重作用域

初期建议：

**同一用户拥有的资源范围内去重。**

后续可以评估：

- 同一共享空间内去重。
- 同一存储实例内去重。
- 全系统去重。

跨用户去重需要额外考虑数据存在性探测、内容证明、加密边界和存储配额问题。

## 8.7 存储引用管理

推荐记录明确的引用关系，以事务保证引用建立和解除操作。

可以维护引用计数作为快速统计字段，但不能只依赖一个不经校验的计数值决定物理删除。

删除前需要确认是否还有有效文件版本、派生资源或其他持久引用。

# 九、Office 在线预览技术选型

## 9.1 为什么不建议自行实现

完整 Office 预览涉及：

- 字体排版。
- 复杂表格。
- 分页计算。
- 页眉页脚。
- 图片定位。
- 公式。
- 图表。
- 幻灯片布局。
- 嵌入对象。
- 格式兼容。

自行实现一个高保真 Office 渲染引擎工作量很大，而且兼容性问题难以解决。

因此不建议从 DOCX、XLSX、PPTX XML 开始自研完整渲染器。

## 9.2 方案对比

| 方案 | 保真度 | 主题自定义 | 资源开销 | 取舍 |
|---|---|---|---|---|
| ONLYOFFICE Docs | 高 | 外壳可控制，内部受限 | 较高 | 可选专业引擎 |
| Collabora Online | 高 | 集成和主题有边界 | 较高 | 备选 |
| Gotenberg + PDF.js | 中高，取决于转换 | 很高 | 转换时消耗资源 | 首选 |
| docx-preview | 常规 DOCX 可用 | 高 | 浏览器侧 | 轻量补充 |
| 自研 Office 渲染 | 难保证 | 完全自由 | 开发成本极高 | 不推荐 |

## 9.3 推荐方案

**默认 Office 预览采用 Gotenberg 转 PDF，再由 PDF.js 在自定义预览器中显示。**

原因：

1. Word 和 PPT 能使用统一的分页预览界面。
2. 页面顶部工具栏由自己控制。
3. 不需要将第三方完整 Office 界面嵌入系统。
4. 可以保留原始文件。
5. 生成的 PDF 可缓存，不必每次重新转换。
6. 未来可以替换转换引擎。

## 9.4 处理流程

```text
上传 Office 文件
       ↓
识别 MIME
       ↓
创建预览转换任务
       ↓
Worker 获取原文件
       ↓
调用 Gotenberg
       ↓
生成 PDF
       ↓
写入预览缓存
       ↓
保存转换状态
       ↓
PDF.js 加载预览文件
```

转换失败时允许下载原文件。

## 9.5 Word 预览

DOC、DOCX：

- 生成分页 PDF。
- 通过 PDF.js 显示。
- 自定义缩放、翻页、搜索和目录 UI。
- 尽量保留文字、表格、图片和分页。

不保证复杂字体、宏及嵌入对象与 Microsoft Office 完全一致。

服务器需要安装合适的中文字体，避免转换后的文字变形或缺字。

## 9.6 PowerPoint 预览

PPT、PPTX：

- 转成 PDF。
- 每页代表一个静态幻灯片。
- 自定义缩略图导航。
- 自定义全屏演示。
- 自定义上一页、下一页。

首期不支持还原复杂动画及幻灯片交互。

## 9.7 Excel 预览

Excel 不建议仅依靠 PDF，因为大型表格转为 PDF 后阅读体验可能不理想。

推荐双模式：

**表格模式**

采用 Apache POI 解析工作表元数据和单元格数据，前端使用虚拟表格渲染。

支持：

- Sheet 切换。
- 分页/分段读取。
- 行列滚动。
- 单元格内容查看。
- 基础格式。
- 合并单元格。

**打印预览模式**

调用 Gotenberg 将文件转换为 PDF。

适用于：

- 查看打印排版。
- 查看固定报表。
- 查看分页效果。

这种双模式兼顾交互体验和排版效果。

不要求自己实现完整 Excel 公式执行或宏引擎。

## 9.8 ONLYOFFICE 的适用位置

ONLYOFFICE 适合作为可选的高保真 Office 引擎。

如果未来需要：

- 更强的格式兼容。
- 文档直接编辑。
- 多人协作编辑。
- Office 原生风格的阅读体验。

可以通过独立 OfficeAdapter 接入。

但应注意：

- 社区版本采用 AGPLv3 并带有相关附加条款。
- 不能擅自去除其品牌和版权标识。
- 集成到不公开源码的产品时需要审查许可证义务。
- 即使仅使用 iframe 或独立服务，也应审查实际集成与分发方式。
- 如果需要专有产品或完整白标能力，应评估商业许可。

截至 2026 年，ONLYOFFICE Docs 9.4 的社区版本已取消过去的 20 个同时连接限制，不能再把旧限制当成当前选型依据。

## 9.9 Office 适配接口

可以设计：

```java
public interface OfficePreviewProvider {

    boolean supports(String mimeType);

    PreviewResult convert(
        String sourceObjectId,
        PreviewOptions options
    );
}
```

实现：

- GotenbergOfficeProvider。
- OnlyOfficeProvider（后续）。
- 其他转换服务适配器。

不要让 FileController 直接调用特定 Office 服务。

# 十、图片预览与编辑架构

## 10.1 图片预览与图片编辑分开

需要区分两个概念：

**预览**

- 缩放。
- 平移。
- 旋转。
- 翻转。
- 全屏。
- 同目录切换。

**编辑**

- 裁剪。
- 添加文字。
- 添加图形。
- 画笔。
- 保存修改后的图片。

当前网盘首要需求是预览，并不需要一开始就实现完整的专业图片编辑器。

## 10.2 图片预览器选型

推荐 Viewer.js。

理由：

- 已具备常见图像变换能力。
- 支持工具栏配置。
- 支持图片集合切换。
- 可以控制部分工具按钮行为。
- 相比自行实现手势、缩放坐标和图片边界处理成本更低。

### 主题处理方式

不要直接照搬默认预览 UI。

建议：

- 自研统一 PreviewShell。
- Viewer.js 负责图片渲染及变换。
- 系统负责外部文件标题、信息栏和操作入口。
- 隐藏不需要的默认控件。
- 统一按钮、背景和交互样式。

如果 Viewer.js 特定版本的内部界面限制较大，优先减少对其内部 DOM 的深层覆盖，而不是依赖不稳定的 CSS 选择器。

## 10.3 备选 PhotoSwipe

PhotoSwipe 更适合沉浸式图片浏览和图库场景。

具备扩展 UI 元素的能力。

如果后续希望做接近相册的连续图片查看，可以评估 PhotoSwipe。

对于当前要求较多的旋转、翻转操作，Viewer.js 更直接。

## 10.4 图片编辑能力

若后续加入实际图片编辑，建议采用：

**Fabric.js + 自定义编辑工具栏。**

Fabric.js 负责 Canvas 对象操作和变换。

系统自行设计：

- 裁剪工具。
- 文本工具。
- 图形工具。
- 保存按钮。
- 撤销重做。

不要让图片编辑和普通图片预览强行共用同一套实现。

## 10.5 图片保存规则

预览中的旋转或缩放不修改原始文件。

如果用户进入编辑模式并保存：

- 默认生成新的文件内容版本。
- 允许选择另存为新文件。
- 触发缩略图更新。
- 触发相关元数据更新。

## 10.6 图片缩略图

缩略图由服务端异步生成。

推荐采用 libvips 或适用的图片处理工具。

缩略图尺寸可按使用场景生成：

- 小图标。
- 列表缩略图。
- 网格预览图。
- 大图预览。

需要处理 EXIF 方向、异常图片尺寸及浏览器不支持的编码。

原始图片与缩略图分别保存。

# 十一、视频播放器与转码架构

## 11.1 视频播放器选型

推荐：

**xgplayer + FFmpeg。**

其中：

- xgplayer 负责浏览器播放和播放器交互。
- FFmpeg 负责探测编码、转封装与转码。
- 后端负责文件权限、播放资源及任务管理。

不建议自行开发完整播放器引擎。

## 11.2 为什么选择 xgplayer

它提供：

- 播放控制。
- 进度控制。
- 倍速。
- 全屏。
- 画中画等浏览器支持的能力。
- 插件扩展。
- 可自定义的控件。
- 常见流媒体播放集成。

对 Vue 3 可以封装独立 VideoViewer 组件管理播放器生命周期。

## 11.3 播放器主题定制

推荐分两层。

### 统一外壳

系统自己的 PreviewShell：

- 顶部文件标题。
- 关闭按钮。
- 下载入口。
- 详情入口。
- 全屏容器。

### 播放器内部

基于 xgplayer：

- 控制条。
- 播放按钮。
- 进度。
- 倍速菜单。
- 音量。
- 清晰度。
- 字幕。
- 播放状态。

优先采用公开插件、配置和 CSS 变量进行定制，不直接修改第三方库源码。

## 11.4 视频格式与编码

需要区分：

- 文件容器：MP4、MKV、MOV、AVI 等。
- 视频编码：H.264、H.265、AV1 等。
- 音频编码：AAC、Opus 等。

浏览器能否播放取决于具体编码组合，而不只是文件后缀。

## 11.5 视频播放策略

采用三级策略。

### 第一级：原生播放

文件编码与浏览器兼容。

直接通过 Range 请求读取源文件。

### 第二级：转封装

编码可被浏览器解码，但原始容器不兼容。

通过 FFmpeg 转封装为兼容容器。

尽量不重新编码。

### 第三级：转码

当原始编码不被浏览器支持时，生成 H.264/AAC 等兼容版本。

根据场景生成 MP4 或 HLS。

## 11.6 转码流程

```text
视频上传成功
      ↓
FFprobe 分析媒体信息
      ↓
生成视频元数据
      ↓
判断是否可直接播放
      ↓
需要转码则创建任务
      ↓
FFmpeg 处理
      ↓
生成 MP4 或 HLS
      ↓
写入派生资源存储
      ↓
更新播放状态
```

## 11.7 视频预览缓存

派生资源可包括：

- 封面。
- 视频缩略图。
- 不同清晰度播放版本。
- 字幕。
- HLS 清单与分片。

所有派生资源应关联原文件的具体内容版本。

当文件内容替换后，新版本不能错误复用旧版本的播放缓存。

## 11.8 Range 请求

对本地、数据库和 S3 存储，读取层应支持合理的范围请求。

服务端需要正确处理：

- Range。
- Content-Range。
- Accept-Ranges。
- 206 Partial Content。
- 416 Range Not Satisfiable。

避免每次视频拖动进度都重新传输整个文件。

## 11.9 转码资源控制

必须限制：

- 同时转码任务数量。
- 单任务 CPU 配额。
- 单任务内存。
- 最大执行时长。
- 临时磁盘使用量。

建议视频转码 Worker 与主 API 进程分离。

FFmpeg 是外部程序，需要校验参数并使用安全的进程调用方式，不通过拼接不受信任的 shell 命令运行。

这是因为音频播放器的基础交互相对视频简单，使用大型音频 UI 库反而可能增加主题定制成本。

## 12.2 功能

- 播放。
- 暂停。
- 进度。
- 音量。
- 倍速。
- 上一首、下一首。
- 循环模式。
- 元数据。
- 封面。

后续若加入波形显示，可评估 wavesurfer.js。

## 12.3 音频编码

浏览器不支持的格式，由 Worker 生成兼容版本。

原始文件保留。

音频元信息及封面可以通过 FFprobe 或专门的元数据工具获取。

# 十三、PDF、Markdown 与代码预览

## 13.1 PDF

推荐 Mozilla PDF.js。

不要只使用浏览器内置 iframe PDF 查看器作为最终实现。

PDF.js 能让系统自行实现：

- 页面工具栏。
- 缩放。
- 连续滚动。
- 页码。
- 缩略图。
- 目录。
- 文本搜索。
- 高亮。
- 阅读位置记忆。

对于大 PDF：

- 按需渲染页面。
- 不同时渲染所有页面的高分辨率 Canvas。
- 及时释放不可见页面的渲染资源。
- 利用 Range 请求按需加载文件内容。

## 13.2 Markdown

推荐：

- markdown-it：Markdown 解析。
- Shiki：代码高亮。
- Mermaid：流程图。
- KaTeX：数学公式。
- DOMPurify：HTML 净化。

Markdown 预览器由系统自研 UI。

支持：

- 渲染。
- 源码。
- 目录。
- 标题跳转。
- 代码高亮。
- 相对图片资源解析。
- 内容搜索。

渲染用户提供的 Markdown 时，应禁用或严格净化危险 HTML，并限制外部资源和脚本执行。

## 13.3 代码和文本

推荐使用：

- Monaco Editor：编辑器级代码浏览能力。
- Shiki：轻量语法高亮。

两者不必同时用于同一个简单文本窗口。

建议：

- 小型代码文件使用轻量文本预览。
- 需要行号、定位、选择、搜索时使用 Monaco。
- 超大日志文件使用服务端分段读取和虚拟列表，而不是一次性装入 Monaco。

## 13.4 大文本处理

例如 1 GB 日志文件。

不允许前端一次性下载并解析完整内容。

服务端提供：

```http
GET /api/files/{id}/text
    ?offset=0
    &limit=65536
```

具体实现需要处理 UTF-8 等多字节字符边界，不能简单任意截断字节后直接解码。

对大文本搜索可采用后台索引或流式扫描。

# 十四、压缩包在线预览架构

## 14.1 技术方案

推荐：

- ZIP、TAR、GZIP、7z 等优先使用 Apache Commons Compress。
- RAR 等未直接支持的格式，通过受控的 7-Zip 处理服务实现。
- 归档内容树由后端解析，前端使用统一目录树组件展示。

## 14.2 压缩包元数据

压缩包预览应解析：

- 内部路径。
- 文件名。
- 压缩后大小。
- 解压后大小。
- 目录节点。
- 文件类型。
- 是否加密。

为了避免重复解析大型压缩包，可以缓存归档目录元数据。

## 14.3 内部文件预览

用户点击压缩包内部文件时：

1. 查询归档目录记录。
2. 验证用户对源压缩包的访问权限。
3. 按需提取指定内部文件。
4. 写入受控临时缓存。
5. 根据类型选择对应预览器。
6. 缓存过期后自动清理。

不能直接把压缩包内的文件写入服务器任意路径。

## 14.4 安全限制

必须防止：

- Zip Slip 路径穿越。
- Zip Bomb 高压缩比攻击。
- 无限递归压缩包。
- 解压文件总数过多。
- 过高的解压后总体积。
- 特殊文件和符号链接访问。
- 恶意归档解析导致进程资源耗尽。

所有解压及解析任务必须设置资源限制。

# 十六、共享空间与共享文件夹权限架构

## 16.1 统一权限模型

共享空间和共享文件夹使用同一套授权计算服务。

但需要区分授权来源：

- 用户为资源所有者。
- 用户为共享空间成员。
- 用户被授予文件夹权限。
- 用户通过分享链接访问。

## 16.2 权限计算

建议统一提供：

```java
PermissionResult checkAccess(
    Long userId,
    Long resourceId,
    ResourceAction action
);
```

操作类型：

- READ。
- PREVIEW。
- DOWNLOAD。
- CREATE。
- UPDATE。
- DELETE。
- MOVE。
- SHARE。
- MANAGE_MEMBER。

## 16.3 权限继承

对于文件夹共享：

```text
共享根目录 A
   ├─ 子目录 B
   │  └─ 文件 C
   └─ 文件 D
```

授权 A 后，默认对子目录 B、文件 C 和文件 D 继承访问权限。

不要求给每一个子文件建立独立授权记录。

后端可以通过祖先关系检查当前文件是否位于共享文件夹内。

## 16.4 共享权限与索引

搜索结果必须基于当前权限范围。

权限变更时：

- 访问 API 立即按新权限判断。
- 搜索索引允许异步更新。
- 预览缓存访问也必须重新校验。
- 快捷入口不具备独立访问权限。

## 16.5 私密空间

私密空间使用额外验证状态。

普通已登录会话不等于已解锁私密空间。

服务端记录经过验证的私密访问会话，并设置有效期及作用范围。

对需要更强保密能力的部署，后续可增加独立加密密钥和密钥生命周期管理。

# 十七、分享链接技术架构

## 17.1 分享令牌

分享链接使用高熵随机令牌。

数据库不应直接存储可用于访问的明文令牌。

可存储令牌摘要并通过索引进行查找。

## 17.2 访问控制

访问分享链接时检查：

- 分享是否存在。
- 是否已过期。
- 是否已停用。
- 是否需要密码。
- 密码是否验证成功。
- 是否已达到下载次数。
- 分享目标是否仍然有效。
- 分享是否被系统策略禁止。

## 17.3 下载地址

对需要实时撤销访问的资源，优先通过后端受控网关或受限代理读取。

S3 预签名 URL 一旦发出，在有效期内不一定能被应用层立即撤销。

因此不能同时承诺「直接签发长效 S3 URL」和「撤销共享后所有已签发 URL 立即失效」。

默认推荐短有效期，并对私密或敏感资源采用网关式读取。

# 十八、缓存与一致性设计

## 18.1 Redis 使用范围

建议用于：

- 登录会话。
- 验证码与频率限制。
- 临时上传任务状态。
- 文件夹直属统计缓存。
- 部分文件元数据缓存。
- 系统配置缓存。
- 短期操作状态。
- 后台任务协调。

不建议将整个用户目录树永久保存在 Redis 中作为唯一数据源。

## 18.2 文件列表缓存

缓存 Key 示例：

`space:{spaceId}:folder:{folderId}:stats`

不建议把不同用户看到的共享目录结果简单缓存为完全相同的未授权文件列表。

## 18.3 缓存失效

文件创建、删除、移动时：

- 失效来源目录缓存。
- 失效目标目录缓存。
- 更新相关统计。
- 发布必要的实时通知。

目录移动可能涉及大量后代，不应通过遍历删除无限数量的 Redis Key 来实现。

可以采用目录修订号、短 TTL 和局部缓存版本控制。

## 18.4 权限缓存

权限缓存的生命周期必须短于普通静态元数据缓存，或者具备可靠的变更失效机制。

共享权限撤销时不允许继续依赖长期未刷新的授权缓存。

# 十九、异步任务架构

## 19.1 异步任务范围

以下任务应进入后台执行：

- 图片缩略图生成。
- 视频元信息解析。
- 视频转码。
- Office 转 PDF。
- 文件正文提取。
- Meilisearch 索引更新。
- 压缩包目录解析。
- 历史文件迁移。
- 大批量文件移动。
- 无引用对象清理。
- 历史版本清理。

## 19.2 队列选型

首期推荐：

**MySQL Outbox + Redis Streams。**

原因：

- 无需立即增加独立 MQ 服务。
- Redis 已经存在。
- 支持消费者组。
- 可以重试未确认的任务。
- 适用于当前个人项目规模。

Redis Streams 使用至少一次交付语义，因此消费者必须支持幂等处理。

若未来任务规模更大、路由复杂或需要成熟的死信与运维体系，可以引入 RabbitMQ。

## 19.3 任务状态

统一状态：

```text
PENDING
   ↓
QUEUED
   ↓
RUNNING
   ↓
SUCCESS
```

异常：

- RETRYING。
- FAILED。
- CANCELED。

每个任务记录：

- Task ID。
- 类型。
- 资源 ID。
- 参数。
- 状态。
- 尝试次数。
- 最后错误。
- 创建时间。
- 更新时间。

## 19.4 幂等处理

后台任务可能重复投递。

例如同一个文件的缩略图任务重复执行时，不应该生成无穷多个实际对象。

可通过：

`taskType + resourceVersionId + processingProfileVersion`

生成稳定的任务幂等标识。

## 19.5 任务隔离

建议至少划分：

- 普通轻任务队列。
- 文本索引队列。
- Office 转换队列。
- 视频转码队列。
- 清理与迁移队列。

避免一个大型视频转码占用全部 Worker 资源。

# 二十、文件操作与 10 秒撤销

## 20.1 撤销模型

不建设完整的用户操作历史模块。

只对支持撤销的操作生成短期撤销记录。

例如：

```json
{
  "operationId": "op-1001",
  "action": "MOVE",
  "resourceId": "100",
  "oldParentId": "20",
  "newParentId": "30",
  "expiresInSeconds": 10
}
```

## 20.2 撤销记录存储

可使用 Redis 暂存撤销所需的前后状态、操作版本与过期时间。

需要注意：

- Redis 过期不等于业务操作自动撤销。
- 撤销需要用户主动触发。
- 执行撤销时仍需后端权限检查。
- 文件当前版本或父级变化时要检查冲突。

## 20.3 不可撤销操作

以下操作不提供简单 10 秒撤销：

- 永久删除。
- 不可逆的历史版本物理清理。
- 已经产生复杂协作副作用的部分操作。

对支持撤销的批量任务，需要记录每项操作结果，而不是简单把整批操作视为无条件可逆。

# 二十一、用户认证与后台权限

## 21.1 身份模型

一个 User 可以对应多个 UserIdentity。

支持：

- 用户名。
- 手机号。
- 邮箱。
- 第三方身份。

身份绑定与用户资源所有权分离。

## 21.2 登录安全

建议采用：

- Spring Security。
- Argon2id 或经过审查的自适应密码哈希算法。
- Access Token + Refresh Token 或等效服务端会话方案。
- 设备会话管理。
- 登录频率限制。
- 验证码防刷。
- OAuth2 / OIDC 标准授权流程。

Cookie 方案需要正确配置 HttpOnly、Secure、SameSite 及 CSRF 防护。

## 21.3 管理员初始化

第一个用户成为超级管理员时必须保证并发安全。

建议通过初始化状态记录、数据库唯一约束和事务完成。

不能采用：

```text
查询用户数量 = 0
直接赋予管理员
```

这种没有并发保护的简单实现。

## 21.4 前后台权限

用户端与管理后台在前端路由层独立。

普通用户访问后台路由展示 404。

但后端管理员接口仍必须返回实际的无权限响应，不依赖前端 404 保护。

# 二十二、文件类型识别与自动分类

## 22.1 识别规则

文件类型不能完全依靠扩展名。

采用：

1. 读取扩展名。
2. 读取客户端 MIME。
3. 服务端通过 Apache Tika 等方式检测内容类型。
4. 根据实际内容和策略决定预览器。
5. 无法识别时回退至通用文件预览。

对不可信文件类型保持保守处理。

## 22.2 分类统计

当前目录分类统计采用数据库聚合或维护计数。

例如：

```sql
SELECT file_category, COUNT(*)
FROM file_node
WHERE space_id = ?
  AND parent_id = ?
  AND deleted_at IS NULL
  AND node_type = 'FILE'
GROUP BY file_category;
```

正式模型可将分类写入文件节点或关联元数据表。

频繁访问的大目录可以维护统计缓存。

## 22.3 递归分类统计

当用户开启「包含子目录」时：

- 使用闭包表或受控递归查询确定范围。
- 通过数据库聚合获取分类统计。
- 不把整棵目录树传到前端再计算。

# 二十四、删除、回收站与垃圾回收

## 24.1 逻辑删除

用户删除文件时：

- 将文件逻辑节点标记为删除。
- 保留版本关系。
- 保留必要的恢复信息。
- 从正常文件列表中隐藏。
- 触发索引可见性更新。

## 24.2 回收站

恢复时检查：

- 原空间是否存在。
- 原父目录是否存在。
- 名称是否冲突。
- 用户是否有权限恢复。
- 存储对象是否仍存在。

## 24.3 永久删除

永久删除分为两个阶段：

1. 业务层解除文件逻辑引用。
2. 后台清理无引用物理对象。

可为物理删除设置安全延迟，减少异常重试和并发任务导致的数据误删风险。

# 二十五、系统安全技术要求

## 25.1 文件访问安全

必须实现：

- 文件级和空间级授权。
- 分享凭证校验。
- 防止 IDOR 越权。
- 防止目录穿越。
- 文件名合法性检查。
- 文件 MIME 校验。
- 不信任客户端 Hash。
- 不执行上传的代码或脚本。
- 对不安全内容使用附件下载或安全隔离预览。

## 25.2 转换服务隔离

Gotenberg、FFmpeg、归档解析及内容提取工具处理的是用户上传的不可信文件。

应部署在限制网络和资源权限的环境中：

- 非特权容器。
- 文件系统最小权限。
- 限制外部网络访问。
- CPU 和内存限制。
- 超时控制。
- 临时目录清理。
- 限制进程数量。

尤其需要防止文档中的远程引用或恶意内容触发内部网络访问。

## 25.3 私密空间安全

私密空间需要服务端二次验证。

未解锁时禁止：

- 获取目录。
- 获取缩略图。
- 获取原文件。
- 搜索私密正文。
- 获取历史版本。
- 生成分享链接。

如果未来增加真正的内容加密，应单独设计密钥派生、数据加密密钥、密钥轮换、恢复和多设备访问方案。


可选增加：

```text

```

FFmpeg 可安装于专门的媒体处理 Worker 容器。

## 26.2 资源分级

以下为初始规划参考，而不是性能保证。

### 基础版

适合个人和少量用户。

- 4 核 CPU。
- 8 GB 内存。
- SSD 存储。
- 本地文件存储。
- API + MySQL + Redis。

不推荐在该配置上同时进行大量 Office 转换和视频转码。

### 完整功能版

适合启用全文索引及文档转换的部署。

- 建议 8 核及以上。
- 建议 16 GB 或以上内存。
- SSD 存储。
- 独立 Worker。
- Meilisearch。
- Gotenberg。
- Tika。

实际所需配置取决于并发量、文档规模、索引体积和转码任务数。

## 26.3 Nginx

负责：

- HTTPS。
- 静态资源。
- API 反向代理。
- 上传请求。
- 下载流。
- 缓存头。
- Range 请求。
- SSE 代理。

需要针对大文件上传正确配置请求体大小、缓冲和超时策略。

## 26.4 数据目录

建议：

```text
/data/cloud-drive/
│
├─ mysql/
├─ redis/
├─ search/
├─ storage/
├─ previews/
├─ uploads/
├─ worker-tmp/

```

临时目录必须具备过期清理机制。

## 26.5 前后端独立构建

pnpm Workspace 可以按应用构建：

- `web`
- `admin`
- `packages/ui`

Java 通过 Maven 模块关系构建需要的模块。

部署时将前端静态资源、API 镜像、Worker 镜像作为独立部署单元。

不需要因为只修改了用户端 UI 就重新构建所有文件处理服务。

# 三十、主要技术取舍汇总

| 技术问题 | 推荐决定 | 不采用方案的主要原因 |
|---|---|---|
| 微服务还是单体 | 模块化单体 | 微服务成本过高 |
| 文件树存储 | 邻接表 + 可选闭包表 | Nested Set 更新复杂 |
| 文件名搜索 | MySQL + 搜索引擎 | 普通 B-Tree 不适合任意模糊匹配 |
| 正文搜索 | Tika + Meilisearch | 实时全文扫描成本高 |
| Office | Gotenberg + PDF.js | 自研 Office 排版困难 |
| 高保真 Office | 可选 ONLYOFFICE | UI 和许可证约束 |
| 图片查看 | Viewer.js | 自研变换与手势成本高 |
| 图片编辑 | 后续 Fabric.js | 首期不必提供完整编辑 |
| 视频 | xgplayer + FFmpeg | 自研播放器与编码困难 |
| PDF | PDF.js | 浏览器 iframe 交互不可控 |
| 音频 | 原生 Audio + 自定义 UI | 简单能力不需要重型库 |
| 压缩包 | Commons Compress + 受控 7-Zip | 浏览器解析大型归档成本高 |
| 分片上传 | Uppy Core + 自定义协议 | 保持对存储适配的控制 |
| 上传标准化 | tus / tusd 预留 | 首期额外协议接入成本 |
| 文件去重 | BlobObject 引用模型 | 文件节点直接绑定物理 Key 不利扩展 |
| 异步任务 | Outbox + Redis Streams | 暂不需要复杂 MQ |
| 实时通知 | SSE | 目前缺少双向实时协同需求 |
| 容器部署 | Docker Compose | 首期无需 Kubernetes |
| 备份 | 独立专题 | 需要同时设计数据与文件恢复 |

# 三十三、最终架构结论

本系统的技术核心不是某一个组件，而是以下六个架构边界：

**1. 逻辑文件系统**

基于数据库维护空间、文件夹和文件，独立于物理存储路径。

**2. 文件内容与版本系统**

以版本和 BlobObject 为中心管理文件内容，为去重、秒传及历史恢复提供基础。

**3. 统一存储适配系统**

以存储配置实例定位真实内容，保证不同存储后端可以并存和切换。

**4. 专业文件预览系统**

通过统一 PreviewShell 与插件注册机制接入 Viewer.js、PDF.js、xgplayer、Gotenberg 等成熟能力，保持系统级 UI 统一。

**5. 独立全文检索系统**

使用 MySQL 承担结构化查询，Meilisearch 承担全文检索，Apache Tika 负责正文提取，通过异步事件维护索引。

**6. 共享与授权系统**

通过统一的资源权限服务处理空间成员、共享文件夹、分享链接及私密空间访问。

**总体决定：采用模块化单体架构，优先自研业务体验和可扩展边界，复杂文件处理尽可能复用成熟开源技术，避免重新实现文档排版、视频编解码和全文索引等高复杂度基础能力。**
